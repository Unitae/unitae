# Internationalization

## Overview

Unitae uses **Paraglide JS** (from the Inlang ecosystem) for internationalization. Translations are compiled at build time into tree-shakeable message functions — no runtime dictionary lookup.

- **Default language**: `fr`, `DEFAULT_LOCALE` in `app/shared/utils/language.ts`. It applies when
  neither the account nor its congregation chose a language, and a new congregation starts in it.
- **Base locale**: `en` (`sourceLanguageTag` in `project.inlang/settings.json`). Paraglide uses it
  only as the fallback for a message a language does not have yet, so a partial translation shows
  English rather than French. Never use `baseLocale` to mean "the default language".
- **Supported locales**: the `languageTags` in `project.inlang/settings.json`. Code reads them from
  Paraglide's `locales`, never from a hand-written list.

## File Structure

```
app/
└── i18n/
    ├── messages/
    │   ├── en.json          # English translations
    │   └── fr.json          # French translations (base locale)
    ├── paraglide/           # Auto-generated (gitignored)
    │   ├── messages.js      # Main export — import * as m from '~/i18n/paraglide/messages'
    │   ├── messages/        # Individual message modules (tree-shakeable)
    │   ├── runtime.js       # getLocale(), setLocale(), locales, baseLocale
    │   ├── server.js        # Server-side middleware
    │   └── registry.js      # Formatting (Intl.PluralRules, NumberFormat, DateTimeFormat)
    └── project.inlang/      # Inlang project config (manages Paraglide)
```

The `app/i18n/paraglide/` directory is auto-generated by the Vite plugin and gitignored. Never edit files there directly.

## Usage

### In components and server code

```typescript
import * as m from '~/i18n/paraglide/messages'

// Simple message
m.error_boundary_title()

// With parameters
m.greeting({ name: 'Jean' })

// Override locale
m.greeting({ name: 'Jean' }, { locale: 'en' })
```

### Message format

Messages use the Inlang message format in JSON:

```json
{
  "greeting": "Bonjour {name}",
  "error_limit_reached": "Limite atteinte pour {resource}.",
  "doc_link": "{#link to=|/docs|}Lire la documentation{/link}"
}
```

- Parameters: `{variable}`
- Rich text: `{#tagName}...{/tagName}` (requires custom renderers)
- Keys are `snake_case`
- Typography, in both languages: the apostrophe `’` and the ellipsis `…`, never a straight `'` or three dots.
  `app/i18n/messages.test.ts` fails the unit suite on either.

### Plurals

A message that shows a count is **one plural message**, never a `_one` / `_other` pair picked in
code: languages do not split numbers the same way (French puts 0 with 1; Ukrainian and Russian have
one form for 1, 21, 31…, another for 2–4, another for 5–20). The language picks the form:

```json
"groups_list_publishers": [{
  "declarations": ["input count", "local countPlural = count: plural"],
  "selectors": ["countPlural"],
  "match": {
    "countPlural=one": "{count} publisher",
    "countPlural=*": "{count} publishers"
  }
}]
```

```typescript
m.groups_list_publishers({ count: publishers.length })
```

- Always end with the catch-all `=*` branch: a form a language does not define falls back to it.
- Each language writes the forms it needs: `one` and `*` in English and French; `one`, `few`, `many`
  and `*` in Ukrainian and Russian.
- A different sentence for exactly one item (« Un document y est déjà ») is an exact `countExact=1`
  branch before the plural ones: see `board_form_highlight_others`.
- The count that picks the form can differ by language. English agrees with the total in « {filed} of
  {due} reports », French with the first number in « {filed} rapports sur {due} »: each language
  declares its own selector.
- Two counts that each drive their own words (« 3 documents · 2 sections ») are two plural messages,
  composed in code or passed into a frame message: see `campaigns_scope_change_flash`. One message
  cannot carry two plural choices without multiplying its forms in every language.
- Zero keeps its own message when the text is entirely different (« No one will see it »): branch on
  `count === 0` in code, and call the plural message otherwise.

`app/i18n/plural-messages.test.ts` renders every plural message for 0, 1, 2, 5 and 21 in every
language and fails on anything left unfilled.

## Adding or Modifying Translations

1. Add or edit the key in `app/i18n/messages/fr.json`
2. Add the corresponding translation in `app/i18n/messages/en.json`
3. The Paraglide Vite plugin recompiles automatically during `pnpm start:dev`
4. Import and use: `m.your_new_key()`

Word both languages with the terms in [Translation Glossary](translation-glossary.md): it fixes the
official congregation vocabulary (congregation, territory assignment, field service report…) in
English and French.

French and English always carry every key. In another language, a missing key falls back to the
`en.json` value.

## Which Language Applies

Paraglide's `getLocale()` is overridden once for the whole process, web server and worker alike, by
`app/shared/utils/locale-scope.server.ts`: it returns the locale of the enclosing
`runWithLocale(locale, fn)`, or `DEFAULT_LOCALE` outside of one. Every `m.*()` call without an
explicit `{ locale }` follows it. Never call `overwriteGetLocale()` anywhere else: the runtime keeps
a single override, and a second one would replace the first, whichever module loaded last.

### In a request

The root middleware `requestLocale()` (`app/shared/middleware/locale.server.ts`) resolves the
locale before any loader, action or resource route runs, and runs the rest of the request inside
`runWithLocale`. The order (`resolveLocaleFromRequest` in `app/shared/utils/locale.server.ts`):

1. The signed-in account's own language, `UserAccount.locale`, chosen in **My profile**
2. That account's congregation's language, `Congregation.locale`, set in **Settings › General**
3. The congregation the request's subdomain or custom domain belongs to
4. Single-tenant: the first congregation
5. `DEFAULT_LOCALE` (`fr`)

Both columns are free text: a value the app does not ship is skipped. `entry.server.tsx` reuses
what the middleware resolved, and resolves the locale itself only for a path no route matches,
since React Router skips middleware for those (404, 405).

The client translates with the `PARAGLIDE_LOCALE` cookie (Paraglide's `cookie` strategy). The
middleware writes it on every response, documents and data requests alike, whenever it differs
from what the request carried. Components already on screen do not re-render when it changes, so
a new language only shows on a full page load: the actions that change one (the general settings
and `/me/language`) answer with `redirectDocument`.

### In an email

An email addressed to one account goes out in that account's language, whoever triggered it:
wrap the send in `runWithLocale(accountLocale(account, congregation.locale), ...)`. The password
reset and verification senders and the notification emails do. Resend renders the React body
inside `sendEmail`, so the body follows the locale active there. Messages meant for the
congregation at large stay in its language, passed explicitly (the assignment messages of
`features/events` take `cong.locale`).

## Worker and Background Job Locale

Background jobs (emails, sync) run outside a web request, so there is no request-level locale. The worker uses `AsyncLocalStorage` to thread locale through the call stack.

**File:** `app/shared/utils/worker-locale.server.ts`

```typescript
import { runInWorkerContext } from '~/shared/utils/worker-locale.server'

// In an email handler:
await runInWorkerContext(congregation.locale, congregation.timezone, async () => {
  // All m.*() calls resolve to the congregation's locale
  await mailer.emails.send({ subject: m.email_subject(), ... })
})
```

`runInWorkerContext` sets the locale through `runWithLocale` (see [Which Language Applies](#which-language-applies)) and keeps the timezone in its own store, read with `getWorkerTimezone()`. Inside it, the notification emails switch to each recipient's language per message.

## Vite Plugin Configuration

The plugin is configured in `vite.config.ts`:

```typescript
import { paraglideVitePlugin } from '@inlang/paraglide-js'

paraglideVitePlugin({
  project: './app/i18n/project.inlang',
  outdir: './app/i18n/paraglide',
})
```

## Formatting Dates, Numbers and Names

Pass `getLocale()` (from `~/i18n/paraglide/runtime`) to every `Intl` formatter, `toLocale*String`,
`toLocaleUpperCase`/`toLocaleLowerCase` and `localeCompare`. It answers the request's language on
the server and the cookie's in the browser, so both render the same text. Never hard-code `'fr-FR'`
or `'fr'`, and never call these methods without a locale: the server would format in its own
language. `en` formats the US way (November 9, 2026), as Intl does by default.

The only exceptions are formatters that read numbers back for a calculation (`formatToParts` for
time zones in `event-time.ts`, `zoned-now.ts`): they keep a fixed `'en-US'` on purpose.

Name a language with `languageLabel(locale)` from `~/shared/utils/language`: « Українська
(Ukrainien) », the language in itself and then in the viewer's. Where each person picks their own
language (Mon compte), `languageName(locale)` gives the language in itself alone: « Українська ».

## Testing with Translations

Unit and integration tests run with `getLocale()` pinned to `DEFAULT_LOCALE`
(`app/tests/locale-setup.ts`), so real messages come out in French as they would outside a request.

In unit tests, mock the entire messages module rather than importing real translations:

```typescript
vi.mock('~/i18n/paraglide/messages', () => ({
  dashboard_greeting: ({ name }: { name: string }) => `Bonjour ${name}`,
  error_not_found: () => 'Not found',
}))
```

This keeps tests independent of translation file changes and avoids Paraglide compilation dependencies in the test environment.
